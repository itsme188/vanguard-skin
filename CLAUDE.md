# Vanguard Skin v2

Local-first portfolio dashboard for tracking Vanguard + IBKR investments.

This is primarily a TypeScript project with some Python utilities. Use TypeScript conventions, proper type safety, and avoid type assertion workarounds unless necessary.

## Tech Stack

- **Framework:** Next.js 16, React 19, TypeScript 5
- **Database:** SQLite via better-sqlite3 (WAL mode, foreign keys ON)
- **Styling:** Tailwind CSS 4
- **Charts:** Recharts (portfolio-level), LightweightCharts v5 (per-security candlestick)
- **CSV parsing:** papaparse
- **PDF parsing:** Claude API (@anthropic-ai/sdk)
- **Chat:** AI SDK v6 (`ai`, `@ai-sdk/react`, `@ai-sdk/anthropic`)
- **Email:** Resend SMTP for outbound (briefing/digest/earnings from `myportfoliodesk.com`); Gmail googleapis OAuth 2.0 + IMAP for inbound newsletter ingestion only
- **Testing:** Vitest
- **Desktop:** Electron (standalone Next.js + system Node.js for native modules)

- **Security Detail** — `/dashboard/security/[id]` hub page per security (chart, positions, lots, notes, events, factors, trade grades)
- **Watchlist** — Track securities not yet owned, with price targets and thesis
- **Trade Reviews** — Monthly AI trade analysis at `/dashboard/analysis?view=trade-reviews` (relocated from Research in Phase 5, 2026-04-30; old `/dashboard/research?view=reviews` URL redirects). Migrations 016 + 021 + 047. Two-phase: Sonnet Q&A → Opus review. Account-specific profiles (IBKR/Vanguard/Roth). GroupedTrade abstraction (lots → trades). Auto model selection (>20 trades → Sonnet, capped at 64k output tokens, 5000+400/trade). **Column-naming rule (2026-05-04 / migration 047):** the AI's structured-output fields are `assessment` / `what_worked` / `what_didnt`. Post-migration these go into DB columns `assessment` / `what_went_well` / `what_went_wrong` respectively. Pre-migration rows used `entry_thesis` / `exit_assessment` / `what_went_well` (with `what_went_wrong` always NULL); readers fall back to those when the new columns are absent. **Never** add a new reader that uses the legacy column names without checking `pragma_table_info('trade_roundtrips')` for `assessment` first — the API route + Security Detail page show the pattern. **Period-high computation** (`lib/trade-review/market-context.ts::getStockPriceContext`) merges `ohlcv_bars` + `prices` into a unified per-date map and folds the trade's own entry/exit prices into the range — neither table is preferred outright, and the trade's actual fill prices guarantee the period range encompasses what really happened. Defensive against the two pipelines drifting apart (TWS daily-bar sync vs daily-snapshot prices). **Pre-save guard** in `generateTradeReview` throws "AI returned an incomplete response" when `result.review_markdown` is empty/missing — without this, output-token truncation surfaces as the misleading SQLite NOT NULL constraint error. Prompt instructs Claude to write `review_markdown` first as additional defense.

## Data Flow

All imports follow: **Detect → Parse → Preview → Confirm → Commit**

1. User drops file(s) on import tab
2. `/api/import?mode=preview` detects format and parses
3. UI shows preview with counts and sample records
4. User clicks Import → `/api/import?mode=commit` writes to DB
5. Every import creates an `import_batches` record for undo
6. Post-commit: auto-classifies securities + auto-computes tax lots + recomputes daily valuations (silent, non-blocking)

## Auto-Refresh & Data Confidence

On TWS connect (auto or manual), `lib/tws/auto-refresh.ts` orchestrates a 6-step pipeline:
1. `syncPortfolio()` — positions + account values + live prices (15s)
   1.5. `purgeExpiredOptionHoldings(db)` — sweeps holdings for expired options (1-day grace). Statement imports never zero-out positions that simply disappear from the next snapshot, so expired options would otherwise linger forever and surface in briefings / cross-account rollups (see `lib/mutations/expired-options.ts`).
   1.6. `purgeClosedOptionHoldings(db)` — sibling to 1.5 for explicitly closed options.
   1.7. `purgeMaturedBondHoldings(db)` — sibling for matured T-bills + bonds (1-day grace). Same root cause as 1.5: statement imports never zero-out maturity-disappeared rows, so matured bonds linger in scenario rate-shocks + fixed-income analytics until manually cleared (see `lib/mutations/matured-bonds.ts`). Also runs as a post-commit hook in `commitImport` for holdings-snapshot sources (`vanguard-pdf`, `vanguard-export`, `vanguard-holdings`, `ibkr-holdings`, `ibkr-activity`) so PDF imports clean up the same day.
   1.8. `reconcileClosedEquityHoldings(db)` — sibling to 1.5–1.7 for closed **stock/ETF** positions, but **snapshot-diff** (not attribute/transaction) based. Equities have no expiry/maturity AND the local trade ledger is often incomplete (statements lag), so the authoritative "is this closed" signal is the broker/statement snapshot itself: any equity absent from an account's latest *full* holdings snapshot (newest `as_of_date`) gets a `quantity = 0` row at that date. **Non-destructive** (preserves cost-basis/history), **self-healing** (a later real sync writes a newer row that wins), **idempotent**. **Shrink guard**: skips an account whose latest snapshot is empty or `< 50%` of the prior snapshot's position count, so a partial/failed TWS sync or under-extracted Vanguard PDF can never wipe the book (under-reconcile self-heals next cycle; over-reconcile would be unrecoverable). Also runs as a `commitImport` post-commit hook (same holdings-snapshot sources as 1.5–1.7). Shipped 2026-06-02 (`58479c3`) after a TWS sync left 35 phantom IBKR equities; see `lib/mutations/closed-equity.ts`. Surfaced via the IBKR Claude connector reconciliation — connector assessment at `docs/plans/2026-06-01-ibkr-connector-assessment.md` (Tiers 2/3 = TWS-independent + cloud IBKR Web API data paths, deferred).
2. `enrichSecurities()` — TWS contract details for unenriched securities (rate-limited, skipped if none)
3. `fetchSnapshotPrices()` — current prices for ALL held securities (~2 min, NOT rate-limited)
4. `computeDailyValuations()` — recompute with fresh prices (instant)
5. `fetchBenchmarkPrices()` — benchmark ETFs, incremental (parallel with steps 3-4)
6. `detectAndFireAlerts()` + `generateSuggestionsForPendingAlerts()` — scan active `security_levels` against fresh prices, insert `level_alerts` + Claude one-sentence recommendations

- **Sync state**: `lib/tws/sync-state.ts` — globalThis singleton tracking status, phase, progress. UI polls `GET /api/tws/sync-status` (3s during sync, 30s when idle).
- **Mutex**: `isSyncing()` prevents concurrent runs. Second call returns immediately.
- **Background refresh**: `lib/hooks/useAutoRefresh.ts` triggers quick refresh (snapshot + valuations only) every 30 min while connected. Configurable via `refreshIntervalMinutes` in Electron settings (0 = disabled).
- **Data confidence**: `lib/queries/data-confidence.ts` scores 5 dimensions (price freshness 40%, holdings recency 25%, cash accuracy 15%, enrichment 10%, valuation coverage 10%). `DataConfidenceIndicator.tsx` replaces `DataFreshness.tsx` in header — shows score, colored dot, popover with dimension bars and actionable fix buttons. Polls `GET /api/data-confidence` every 60s.
- **Data quality labeling**: Migration 026 adds `data_quality` column to `daily_valuations` (`live`/`recent`/`estimated`/`computed`). Set by `computeDailyValuations()` based on price staleness. Account cards show "(est.)" for stale data; portfolio total shows "~" prefix when estimated.

## Conventions

- All DB query functions live in `lib/queries/` — read-only
- All DB mutation functions live in `lib/mutations/` — writes
- Every DB function takes a `db: Database.Database` parameter (dependency injection for testing with `:memory:` DBs)
- All dates use `YYYY-MM-DD` format
- Monthly snapshots use last-day-of-month dates (or today's date for TWS live snapshots with `source='tws'`)
- Every imported record gets a deterministic `source_key` — re-import is a no-op
- Every import creates an `import_batches` record with undo capability
- Transaction types are UPPERCASE: BUY, SELL, DIVIDEND, REINVESTMENT, TAX_WITHHELD, BUY_TO_OPEN, SELL_TO_CLOSE, etc.
- `computeTaxLots` matches on uppercase BUY/SELL — parsers must output uppercase
- Market values use `adjustedMarketValueSQL()` from `lib/valuation.ts` — handles bonds (÷100) and options (×multiplier). Uses `LOWER()` for case-insensitive type matching.
- **Security type casing**: DB stores capitalized types (`Bond`, `Stock`, `ETF`, `Option`, `Mutual Fund`). Always use case-insensitive comparisons (`.toLowerCase()` in TS, `LOWER()` in SQL). `mapSecurityType()` is centralized in `lib/tws/security-type-map.ts` — import from there, never duplicate. A PostToolUse lint hook in `.claude/settings.json` rejects new case-sensitive comparisons. Enforced at the write boundary by `lib/mutations/securities.ts::upsertSecurity` which normalizes lowercase strings ("stock", "option", etc.) to canonical capitalized form, plus YYYYMMDD `expiration_date` / `maturity_date` to ISO YYYY-MM-DD — defense-in-depth against malformed values from any new writer (TWS contractDetails was the historical offender). **Also defaults option `multiplier` to 100 when missing/≤1** (2026-06-05, `94dbce9`): listed equity/ETF options always carry a 100× contract multiplier, but the canonical CSV format has no multiplier column, so a new option security otherwise lands at NULL → `COALESCE(multiplier,1)` → valued at 1/100th with the shortfall leaking into inferred cash. TWS enrichment sets it; this covers writers that don't. `scripts/fix-option-multipliers.ts` is the one-shot repair for rows written before the fix (backfill + recompute valuations).
- **Import validation**: `lib/import/validate.ts` runs before commit — validates dates, quantities, prices, transaction types, AND financial sanity (`isGarbageSymbol()` rejects timestamps, commas, >30 chars, purely numeric). Bad rows excluded with warnings.
- **API contract tests**: `tests/contracts/api-component-contracts.test.ts` verifies compute function return shapes match component expectations. Add a test here whenever a new client component fetches from an API.
- **Account scoping rule**: If a page has an account scope selector (e.g., Analysis), EVERY query on that page must accept and respect `accountIds`. No global queries on scoped pages. Client components pass `scope` prop; API routes resolve via `resolveScopeToSingleId()` or `resolveScope()` from `lib/queries/accounts.ts`. **Scopes are disjoint:** `vanguard` excludes any account whose name contains "roth", so `all = vanguard + roth + ibkr` partitions the portfolio. Without the disjoint rule, the Roth scope would just be a subset of Vanguard scope and selecting either would surface overlapping data.
- **Multi-account compute scope — `accountIds[]`, never first-id (2026-06-01, `a54c42f`)**: the three scope-aware compute fns `computeFactorAnalysis` / `computeRiskMetrics` / `computePositionRisk` accept BOTH `accountId?: number` (legacy) and `accountIds?: number[]` (multi-account), normalized by `lib/compute/factors.ts::normalizeAccountIds` (precedence: `accountIds` array wins; lone `accountId` wraps to `[id]`; neither → undefined = whole portfolio). Internally they thread `IN (...)` filters through `computeTilts`/`computeConcentration`/`computePositionRisk` and pull the valuation series from `getDailyValuationsForAccounts(db, accountIds)` (sums per-date across the set BEFORE drawdown/vol/Sharpe — per-account stats can't be averaged into a portfolio figure). **Never collapse a multi-account scope to `accountIds[0]`** — that silently drops every other account (the bug `buildContextForSurface` + `macro-themes.ts` had). When feeding these fns from a scope, pass the full `resolveScope()` array. Back-compat: `{accountIds:[1]}` is byte-identical to `{accountId:1}` (deep-equal-guarded). The `/api/compute/*` routes stay on `resolveScopeToSingleId` deliberately — correct for the current 1-account-per-named-scope structure (`"all"` → null → all-accounts path).
- **Calendar date utilities**: `lib/calendar/date-utils.ts` is the single source of truth for Monday calculations (`getCurrentMonday()`), date arithmetic (`addDays()`), week range formatting (`formatWeekRange()`), and weekOf validation (`validateWeekOf()`). Never create local date functions — import from here.
- **ET-anchor every "today / this week / outbound-email date" (2026-05-29).** The portfolio is ET-centric (markets, statement dates, calendar events) but the Mac travels (foreign local TZ) and the Cloudflare Worker runs in UTC — so a runtime-local `new Date()` silently targets the wrong day/week. **Rule:** (1) for "what day is it" use `lib/calendar/date-utils.ts::todayET()` (mirrored by `workers/cron/src/dst.ts::todayET`); `getCurrentMonday()` is already ET-anchored via `Intl.DateTimeFormat("America/New_York")`. (2) **Never** `new Date().toISOString().slice(0,10)` for a user-facing "today" — that's UTC. (3) **Every human-facing date string in an outbound email** must pass `timeZone: "America/New_York"` to `toLocaleDateString` (Mac `send-digest`/`send-evening`/`daily-digest`/`group-by-company`/`briefing-html`; Worker `fallback-digest`/`fallback-evening`/`html.ts`); a no-timeZone call renders the traveling Mac's local date or the Worker's UTC date — both surface as "every email's date is a day off." (4) Worker briefing weekOf uses `briefingWeekOf()` (= getCurrentMonday semantics: Sun→next Mon, Mon→this Mon), NOT a "next Monday from now" that jumps a week on a Monday. - **Holdings upsert priority — statement data wins over TWS intra-day rows**: same pattern as snapshots, applied to holdings. `lib/import/engine.ts` holdings insert uses `ON CONFLICT(account_id, security_id, as_of_date) DO UPDATE … WHERE holdings.source_key LIKE 'tws-%'`. Pre-2026-05-04 used INSERT OR IGNORE and 18 of 19 IBKR statement holdings were silently dropped on April-2026 import because TWS sync had run earlier in the day. Statement re-imports remain idempotent because the WHERE clause filters out non-tws source_keys.
- **Compare timestamps with SQLite `datetime()` on BOTH sides, never as raw strings**: `research_articles.received_at` and similar columns are written via `datetime('now')` in space-separator form ("2026-04-22 22:53:41"). Caller-supplied filters often arrive in ISO-Z form from `new Date().toISOString()` ("2026-04-22T13:44:44.806Z"). Under raw string compare, space (ASCII 32) < 'T' (ASCII 84), so space-format timestamps sort earlier than T-format ones even when the actual moment is later — silently returning zero rows. Always wrap both sides in `datetime()` when comparing timestamps that may mix formats. Shipped 2026-04-23 (`57d9c26`) after the "send digest since last email" bug.
- **Snapshot range boundaries BEFORE long awaits in concurrent endpoints**: `lib/digest/send-digest.ts::sendDigestEmail` reads `getLastDigestSentAt(db)` at function entry into a local `sinceSnapshot` variable, NOT inside the `since_last` branch which would run AFTER `syncPortfolio` + `fetchNewArticles` + `processUnprocessedArticles` (60-90s of awaits). Otherwise a concurrent manual trigger that completes during that window updates `last_digest_sent_at` to "now" and the cron path then reads a future-of-our-articles cutoff → zero matches → silent skip. This race produced 3 weekdays of mystery skips (Apr 22-24 2026). Pattern applies anywhere two paths can update the same "last X done" timestamp while one of them is mid-process. Regression test: `tests/digest/send-digest-race.test.ts`.
- **Calendar enrichment window is source-aware**: `lib/calendar/enrichment-runner.ts` keeps `MAX_AGE_MS_MACRO = 2h` (FRED/FOMC/nonfred publish data within minutes; immediate market reaction window is what matters) but uses `MAX_AGE_MS_EARNINGS = 12h` for `source = 'finnhub'` OR `event_type = 'earnings'`. A BMO earnings call at 08:00 ET can't produce a meaningful reaction snapshot before 09:30 (market open) — pre-fix the 2h window expired 30 min after market opened, leaving the row unenriched forever (NSC 2026-04-24). 12h lets a single afternoon catch-up capture the full-day reaction. Test: `tests/calendar/enrichment-runner.test.ts::"BMO earnings released 4 hours ago is still in the (12h) earnings window"`.

## Data Integrity

When working with financial data (prices, valuations, dates, events), NEVER use hardcoded or guessed values. Always use authoritative data sources (APIs like FRED, Hebcal, IBKR) instead of generating dates, prices, or financial figures from training data.

When data appears missing or wrong, investigate the root cause (check the API response, query the DB directly) before building UI workarounds. The import engine now derives prices from holdings `market_value` — every holding with a market value produces a price automatically on import.

- **Number rendering on user surfaces — single source of truth**: `lib/format.ts::formatLargeUSD` (≥$1B → `$N.NNB`, ≥$1M → `$N.NM`, ≥$1k → comma-grouped, sub-$1k → 2dp EPS-scale) + `lib/format.ts::parseLargeUSD` (accepts `$4.34B` / `4340M` / raw / commas). Anywhere a Finnhub-shaped string `"EPS X.XX · Rev N"` reaches the user goes through `lib/format/finnhub-figure.ts::formatFinnhubFigure[Compact]` first — never render the raw string. Applies to: EarningsHub rows, TodayReleases est line, EnrichmentRowSummary, EnrichmentDetail, email scoreboard, BogeysEditModal display. Pure formatters at the file level (`formatUSD` / `formatPercent`) still ok for LLM prompts, CSV exports, aria-labels.

- **Risk-free rate — single source of truth**: `lib/queries/risk-free-rate.ts::getRiskFreeRate(db)` reads the cached FRED DGS3MO 3-month T-bill rate from `settings` (key `risk_free_rate`), falls back to 0.045 if never fetched OR if the settings table doesn't exist (in-memory test DBs). Used by `lib/compute/risk.ts` (Sharpe ratio) + `lib/compute/options-greeks.ts` (Black-Scholes drift) — replaces the prior 0.045 hardcodes. `scripts/refresh-risk-free-rate.ts` is the manual refresh path; cache TTL is 48h via `isRiskFreeRateStale()`. Never hardcode 0.045 in new code — always go through `getRiskFreeRate(db)`.

- **Empty-state shell — `<EmptySection>` instead of silent `return null`**: `app/dashboard/components/EmptySection.tsx` is the single primitive for sections whose data prerequisite is absent. New Analysis sections that may have no data (no held bonds, no options, etc.) should render `<EmptySection>` not `return null` — the page should look intentional, not partially-broken.

- **Per-scope benchmark default + picker pattern**: `app/dashboard/components/FactorAnalysis.tsx` exports `DEFAULT_BENCHMARK_BY_SCOPE` (Vanguard→VTI, IBKR→QQQ, Roth→SPY, ALL→SPY). - **Dual-class symbol resolution — always via `issuerSiblings()`**: `lib/queries/briefing-symbols.ts::getSymbolStatus` walks the issuer family so GOOGL events classify as HELD when user owns GOOG. `getSecurityIdForSymbolWithSiblings` does the same for security_id lookup; `getEarningsForWeekDeduped` post-resolves null `security_id` via family so `<SymbolLink>` fires across class A/B variants. - **`getCrossAccountPositions` cost-basis fallback**: TWS auto-refresh writes intra-day positions with `cost_basis = NULL`. Statement imports write the same (account, security) pair with cost_basis populated on the period-end date. ## External APIs

When working with external APIs (TWS/IBKR, Gmail, FRED), check the correct API contract (parameter names, types, rate limits) before writing code. Do not guess field names like `symbol` vs `conId`.

## Dev Server Gotchas

- After changing any server-side code (SQL queries, API routes, server components), restart the dev server before testing. Next.js dev server caches server-side code aggressively — page refreshes alone won't pick up changes. Stale server code can also make errors appear on the wrong page.
- **Turbopack lock file**: If dev server crashes or terminal closes without Ctrl+C, a stale lock file prevents restart ("Unable to acquire lock"). Fix: `rm -rf .next` then `npm run dev`.
- **TWS stale connection after restart**: The old TCP socket to TWS lingers after dev server restart. New server gets `getCurrentTime timeout (5s)` because TWS is still holding the old client ID 1 session. Fix: in TWS, toggle Edit → Global Config → API → "Enable ActiveX and Socket Clients" off then on to drop stale connections.

- All tests use in-memory SQLite (`:memory:`) for isolation
- Test fixtures in `tests/fixtures/` (anonymized)
- Real data fixtures in `tests/fixtures/real/` (gitignored)
- PDF parser tests use mock Claude API response JSON (`tests/fixtures/vanguard-pdf-claude-response.json`)
- To regenerate PDF fixture: `ANTHROPIC_API_KEY=sk-... npx tsx scripts/generate-pdf-fixture.ts <path-to-pdf>`
- Verify build compiles: `npx next build` (catches issues tests don't)
