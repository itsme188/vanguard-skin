# Conventions — Expanded Detail

This file holds the full rationale, dated provenance, commit hashes, root-cause war-stories, and
regression-test names for the longer rules in CLAUDE.md's `## Conventions` section. CLAUDE.md keeps
the actionable rule + canonical file path only (it is loaded into every session's context, so it
stays tight); read this file on demand when you need the *why* behind a rule.

Each entry below is the original, verbatim convention text as it stood before the 2026-06-05
condensation. The matching CLAUDE.md bullet is the short form.

---

- **Security type casing**: DB stores capitalized types (`Bond`, `Stock`, `ETF`, `Option`, `Mutual Fund`). Always use case-insensitive comparisons (`.toLowerCase()` in TS, `LOWER()` in SQL). `mapSecurityType()` is centralized in `lib/tws/security-type-map.ts` — import from there, never duplicate. A PostToolUse lint hook in `.claude/settings.json` rejects new case-sensitive comparisons. Enforced at the write boundary by `lib/mutations/securities.ts::upsertSecurity` which normalizes lowercase strings ("stock", "option", etc.) to canonical capitalized form, plus YYYYMMDD `expiration_date` / `maturity_date` to ISO YYYY-MM-DD — defense-in-depth against malformed values from any new writer (TWS contractDetails was the historical offender). **Also defaults option `multiplier` to 100 when missing/≤1** (2026-06-05, `94dbce9`): listed equity/ETF options always carry a 100× contract multiplier, but the canonical CSV format has no multiplier column, so a new option security otherwise lands at NULL → `COALESCE(multiplier,1)` → valued at 1/100th with the shortfall leaking into inferred cash. TWS enrichment sets it; this covers writers that don't. `scripts/fix-option-multipliers.ts` is the one-shot repair for rows written before the fix (backfill + recompute valuations).

- **Multi-account compute scope — `accountIds[]`, never first-id (2026-06-01, `a54c42f`)**: the three scope-aware compute fns `computeFactorAnalysis` / `computeRiskMetrics` / `computePositionRisk` accept BOTH `accountId?: number` (legacy) and `accountIds?: number[]` (multi-account), normalized by `lib/compute/factors.ts::normalizeAccountIds` (precedence: `accountIds` array wins; lone `accountId` wraps to `[id]`; neither → undefined = whole portfolio). Internally they thread `IN (...)` filters through `computeTilts`/`computeConcentration`/`computePositionRisk` and pull the valuation series from `getDailyValuationsForAccounts(db, accountIds)` (sums per-date across the set BEFORE drawdown/vol/Sharpe — per-account stats can't be averaged into a portfolio figure). **Never collapse a multi-account scope to `accountIds[0]`** — that silently drops every other account (the bug `buildContextForSurface` + `macro-themes.ts` had). When feeding these fns from a scope, pass the full `resolveScope()` array. Back-compat: `{accountIds:[1]}` is byte-identical to `{accountId:1}` (deep-equal-guarded). The `/api/compute/*` routes stay on `resolveScopeToSingleId` deliberately — correct for the current 1-account-per-named-scope structure (`"all"` → null → all-accounts path).

- **ET-anchor every "today / this week / outbound-email date" (2026-05-29).** The portfolio is ET-centric (markets, statement dates, calendar events) but the Mac travels (foreign local TZ) and the Cloudflare Worker runs in UTC — so a runtime-local `new Date()` silently targets the wrong day/week. **Rule:** (1) for "what day is it" use `lib/calendar/date-utils.ts::todayET()` (mirrored by `workers/cron/src/dst.ts::todayET`); `getCurrentMonday()` is already ET-anchored via `Intl.DateTimeFormat("America/New_York")`. (2) **Never** `new Date().toISOString().slice(0,10)` for a user-facing "today" — that's UTC. (3) **Every human-facing date string in an outbound email** must pass `timeZone: "America/New_York"` to `toLocaleDateString` (Mac `send-digest`/`send-evening`/`daily-digest`/`group-by-company`/`briefing-html`; Worker `fallback-digest`/`fallback-evening`/`html.ts`); a no-timeZone call renders the traveling Mac's local date or the Worker's UTC date — both surface as "every email's date is a day off." (4) Worker briefing weekOf uses `briefingWeekOf()` (= getCurrentMonday semantics: Sun→next Mon, Mon→this Mon), NOT a "next Monday from now" that jumps a week on a Monday. Regression guard: `tests/calendar/date-utils.test.ts` injects UTC instants that fall on a different ET day. Root-caused 2026-05-29 after travel jumbled email dates + "earnings this week" showed last week.

- **Market-holiday gating (2026-05-29)**: `lib/calendar/market-holidays.ts` (+ self-contained Worker mirror `workers/cron/src/market-holidays.ts`, kept in sync via a parity test) is the single source of truth for NYSE full closures. `isMarketHoliday(date)` / `isMarketClosed(date)` (weekend OR holiday) / `nextTradingDay(date)` / `shouldSendBriefingToday(date)`. **Behavior:** daily digest + evening email SKIP on full closures (`/api/cron/digest` + `/api/cron/evening` early-return `skipped:market_holiday`, logged not silent; Worker `runJob` gates digest/evening the same way). The Sunday briefing SHIFTS to Monday when the upcoming Monday is a holiday — `shouldSendBriefingToday` returns true on a normal Sunday OR a holiday Monday and false on a normal Monday; the launchd `send-weekly-briefing.sh` fires at 15:00 ET on BOTH Sun+Mon (sends NO weekOf so the route's gate + ET getCurrentMonday apply), and `parseJobFromClock` fires the briefing slot on dow 0 OR 1. Manual `/internal/trigger` passes `force:true` to bypass the gate. **Holiday list is hardcoded but VERIFIED against nyse.com (2026-05-29) — re-verify before extending past 2027**; the trap is the observed-day shift (e.g. Jul 4 2026 is Saturday → the FULL closure is Fri Jul 3; Jul 2 is only a 1pm early close, NOT a holiday). Early-close days are NOT holidays — the market is open, so emails still send.

- **Claude model IDs**: `lib/claude-models.ts` is the single source of truth — import `OPUS_MODEL` / `SONNET_MODEL`, never inline a model string. Anthropic's API requires specific IDs (no "latest" alias). A typo previously broke 4 features silently (calendar sync, trade reviews, briefings, Gmail processing) when `claude-sonnet-4-7` was used (Sonnet's latest is 4-6).

- **Earnings release times — single source of truth**: `lib/calendar/release-times.ts` has two layers. `RELEASE_TIMES_ET` maps macro `event_type` → wall-clock ET. `SYMBOL_RELEASE_TIMES_ET` maps individual earnings tickers (AAPL=16:30, AMZN=16:01, GOOGL/GOOG=16:01, META=16:05, MSFT=16:05) → wall-clock ET; `earningsHourToReleaseTime(hour, symbol?)` and `resolveReleaseTime({ symbol })` consult the symbol map FIRST, then fall through to BMO/AMC defaults. `lib/mutations/calendar.ts::deriveReleaseTime(eventTime, symbol)` does the same for the manual-insert path. Both bulk Finnhub upsert + manual single-event insert thread the symbol through. Worker mirror not needed — `workers/cron/src/fallback-earnings.ts` only reads `release_time` from snapshot, never writes; Mac-side fix propagates via the nightly R2 snapshot. Add a new symbol via the constant + run `scripts/backfill-symbol-release-times.ts` to update in-DB future rows (idempotent).

- **Per-event email skip**: `earnings_email_skips` (migration 045) lets the user mute one specific (event, phase) pair without globally muting the symbol. `findEmailCandidates` LEFT JOINs both `earnings_emails` (audit) AND `earnings_email_skips` and excludes either via NULL check. UI toggle: `app/dashboard/today/EarningsRowChips.tsx` reveals a red-tinted "skip" button on hover over a pending chip; skipped chips render strikethrough and un-skip on click. New `app/api/earnings/skip/route.ts` is the in-app POST/GET/DELETE — no cron auth (in-app pattern, mirrors `/api/settings/earnings`).

- **Issuer-family normalization**: `lib/securities/issuer-family.ts::issuerSiblings(symbol)` is the single source of truth for dual-class equity symbol siblings (GOOG/GOOGL, BRK A/B variants, FOX/FOXA, NWS/NWSA, UA/UAA, LBRDA/LBRDK, LSXMA/LSXMK, HEI/HEI.A). Use it whenever you need to roll up positions across share classes — e.g., the briefing's `buildCombinedPositionsForEvents` matches earnings events to holdings via `issuerSiblings(event.symbol)` so Vanguard's GOOG common gets linked to GOOGL's earnings event. String-equality joins on symbol miss the class A/B/C cross-match. Add a new family by extending the `FAMILIES` constant; mappings are case-sensitive on the canonical brokerage symbol.

- **Per-(account, security) latest-holdings CTE pattern**: any new compute or query that joins `holdings` to filter by "the latest snapshot per (account, security)" must use this shape, NOT a global `MAX(as_of_date)` subquery. The reason: IBKR auto-refreshes intraday (today's date) while Vanguard statements land at month-end; a global MAX picks today and silently filters out all Vanguard rows. The Slice A Greeks bug (2026-05-10) dropped 52 of 55 option positions due to this pattern violation — see commit `b4483a4`. Two distinct shapes coexist:
  - **`lib/queries/analysis.ts:68+` `LATEST_HOLDINGS_CTE`** internally calls `latestHoldingsPredicate({ keyBy: "account", includeShorts: false })` — keeps the 6 in-file callsites stable while routing through the canonical helper. Allocation queries fold per-security rows under outer SUM, so stale snapshots wash out and the per-account keyBy is intentional.
  - **Per-(account, security) variant** keys on BOTH `account_id` AND `security_id` + filters `quantity != 0` (short positions must surface). **Single source of truth: `lib/queries/latest-holdings.ts::latestHoldingsPredicate({ keyBy?, includeShorts?, asOfDate?, accountFilter? })`** — used by analysis.ts (per-account form) AND 8+ per-(account, security) consumers including `options-greeks` / `options-expirations` / `analysis-trust-state` / `exposure-delta` / `cash-deploy` / `scenario-recipes` / `drill-down` / `computeTilts` / `computeConcentration` / `computePositionRisk` / `security-detail.getHoldingsBySecurity` / `scenarios.ts` / `cost-basis-reconciliation.ts` (last three migrated 2026-05-11). The `asOfDate?: string` option (added 2026-05-11 in P3 Slice D, `fd19296`) literal-substitutes a YYYY-MM-DD date (regex-validated, throws on malformed input) into BOTH the inner `MAX(as_of_date)` subquery AND the outer predicate — used by week-over-week delta call sites. **One exception: `lib/compute/daily-valuation.ts::computeDailyValuations`** keeps an inline `MAX(as_of_date)` subquery because it needs the date as a positional `?` bind (the prepared statement is reused across many target dates in a hot loop); literal substitution would force re-preparing per date. Never re-introduce inline copies elsewhere; this helper is the canonical pattern.

- **TWR reconciliation gate**: `lib/compute/twr-reconcile.ts::reconcileTwrAgainstStatements(db, accountId, periodEnd, options?)` compares computed TWR to statement-reported TWR (`monthly_snapshots.twr`). **Critical: pass `startDate === endDate === periodEnd`** to scope `computeTwr` to a per-month return — without this, computeTwr returns CUMULATIVE TWR from earliest snapshot, which is incomparable to the per-month statement value (97.6% out-of-tolerance pre-fix → 99.2% within 5bp post-fix). Source-format normalization: `ibkr-activity` stores TWR as percentage (divide by 100); canonical/vanguard-pdf store as decimal. `scripts/audit-twr-vs-statements.ts` is the pre-merge gate — exits 1 if >20% out-of-tolerance.

- **Read-through pairs — preview composer integration shipped 2026-05-03 (`9086167`)**: Migration 044 `read_through_pairs` + 14 seeded pairs (PRTO→XMTR, HUN→LIN, 12-pair fan-out of {GOOGL, META, APP, RDDT} as `group_label='ad-platform-2026'`). Two query helpers in `lib/queries/read-through-pairs.ts`: `getReadThroughReporterSymbols(db)` is consumed by `lib/calendar/sync.ts` to merge non-held reporters (PRTO, RDDT) into the Finnhub sweep so their actual + reaction get enriched automatically; `getReadThroughsForTargets(db, family)` powers `buildReadThroughEntries` in the composer. The composer's `renderReadThroughsBlock` slots between newsletters and analyst sections in `renderPreviewPrompt` (per design doc §4) — one bullet per matched reporter with consensus + actual + beat math (EPS as $ delta, Rev as %) + reaction snapshot (stock + SPY + QQQ T+2h) + the pair's hypothesis. Sorted by weight desc, deduped per reporter, 14-day lookback. **Defensive `isPlausibleEarnings` guard** rejects reporters whose Finnhub `actual_value` deviates implausibly from `consensus_estimate` (EPS ratio outside [0.5×, 1.7×] OR Rev outside [0.7×, 1.4×]) — calibrated to keep PWR's real +28% Q1 EPS beat while rejecting GOOGL's stored 5.11-vs-2.70 (1.89×, confirmed bogus by live re-fetch). Recap-side rendering deferred. Design doc: `docs/plans/2026-05-02-stock-to-stock-read-throughs.md`.

- **Finnhub data quality — sanity-guard at consumption time, not source patch**: Finnhub's `epsActual` / `revenueActual` from `/calendar/earnings` drifts in BOTH directions post-release (e.g. GOOGL 2026-04-29 stored EPS 5.11 was bogus and live re-fetch returns 2.62; AMZN's stored 1.56 is actually closer to truth than the live 2.78 re-fetch). `lib/calendar/enrich-actuals.ts::fetchFinnhubActual` writes whatever Finnhub returns at enrichment time — auto-overwriting from live would corrupt the AMZN case. The defense pattern is to validate at the **consumer** (read-throughs builder via `isPlausibleEarnings`) not the writer. `scripts/audit-finnhub-actuals.ts` is the read-only audit tool — it has a `--fix` flag but treat as last resort, NOT a cron. Use the existing `POST /api/earnings/actuals` for one-off overrides; `earnings_bogeys` (TMT Breakout uploads) is the longer-lived user-curated alternative.

- **Daily digest layouts (single source of truth for both views)**: `lib/digest/daily-digest.ts::generateDigestSince(db, sinceDate)` is the per-source layout (the canonical email shape — wraps `getRecentArticles` flat + iterates with `## SOURCE_NAME · *sentiment*` headers). `lib/digest/group-by-company.ts::generateDigestByCompanySince(db, sinceDate)` is the per-company layout (wraps the same `getRecentArticles` call + buckets via `bucketByCompany` — multi-symbol articles fan out across buckets, no-symbol articles collect to a trailing `(no symbol)` macro section). Both share `formatTriggeredAlertsSection` for the alerts block at the top. The morning email itself ALWAYS uses by-source (matches the user's open-the-email mental model + zero deliverability risk); the by-company view is in-app only via `<DigestEmailViewer>` modal + `GET /api/digest/preview` (which returns BOTH pre-rendered HTMLs in one fetch so the modal toggle is instant).

- **Synthesis prompt — coverage-depth ban + held-ticker prioritization (single source of truth)**: `lib/digest/synthesize.ts` `SYSTEM_PROMPT` (as of 2026-05-12, commit `221edc1`) contains two hard rule blocks Sonnet must obey when authoring the synthesized digest. **COVERAGE-CHARACTERIZATION RULES**: never label a source as having mentioned a symbol "only mentioned indirectly / in passing / tangentially / without focus / briefly noted / appeared only as a footnote" — the model cannot tell from bucket summaries whether a symbol was the lead topic or one of many tickers in a list. If a symbol appears in a source's bucket entry, that source covered it — narrate WHAT the source said (drawn from the supplied summary), not HOW prominently. **HELD-TICKER PRIORITIZATION**: every held ticker with ANY coverage in today's buckets MUST get its own `##` section, however brief; held names cannot be relegated to "## Also covered" even on single-article coverage. Regression tests in `tests/digest/synthesize.test.ts` pin both rule blocks' text so the guardrails can't silently drop. Origin: 5/12 morning briefing framed APP as "only mentioned indirectly by TMT Breakout" despite direct coverage.

- **Calendar sync — single source of truth**: `lib/calendar/sync.ts::syncCalendarForWeek(db, weekOf, opts)` is the only place the three-phase ingest (WSH → Claude macro → Finnhub) is implemented. Both `app/api/calendar/sync/route.ts` (SSE bridge for the Calendar UI) and `lib/digest/send-briefing.ts` (in-process call before generation) call this function. **Why this matters:** Sunday 4/26's briefing missed PCE + Q1 GDP because the briefing path only ran TWS sync (`syncPortfolio`) — calendar sync was never on the Sunday auto-cron path. Adding any new "must sync before X" caller now means one library import, not duplicating the SSE-laden route logic.

- **Briefing self-admission regex + auto-regen — single source of truth**: `lib/calendar/briefing-self-admission.ts` exports `buildSelfAdmissionRegex()`, `findSelfAdmissions(text)`, and `buildSelfAdmissionAddendum(matches)`. Patterns catalog phrases like "data looks corrupted" / "I can't verify" / "without access to". Two consumers share this module: (a) the pre-send auto-regen flow inside `generateBriefingTextWithRegen()` in `briefing.ts` (1-shot retry with an addendum that quotes the matched phrases — cap = 1 retry to prevent loops), and (b) `scripts/verify-briefing-content.ts:370` post-gen scanner (failsafe / manual triage). `buildSelfAdmissionRegex()` returns a FRESH RegExp per call because `g`-flag regexes are stateful via `lastIndex` — never cache a module-level singleton. Any tightening of patterns lands in both consumers automatically.

- **Briefing holdings: `quantity != 0` for portfolio context, `> 0` for sector clusters**: `lib/calendar/briefing.ts:65` MAIN holdings query uses `!= 0` so net-short positions surface (per A7, 2026-05-11 `d238aef`); the formatter at `formatHoldingsList()` adds `NET SHORT n` markers when `SUM(quantity) < 0`. The sibling `querySymbolsBySectors` queries at lines ~568, ~585 intentionally KEEP `> 0` because the §6 macro cluster narrates positive sector exposure ("you hold MSFT, AAPL, GOOG in tech") — including shorts there would mislead Opus into framing anti-correlated positions as same-direction sector bets. An inline comment in `querySymbolsBySectors` documents this asymmetry so future "consistency" refactors don't flip them.

- **Price source priority**: Higher-priority sources overwrite lower: tws(1) > ibkr(2) > vanguard(3) > manual(4). See conditional upsert in `engine.ts`. **Prices derived from holdings (`marketValue / quantity` in step 4b of `commitImport`) inherit the parser's `sourceType` via `holdingDerivedPriceSource()` — not a hardcoded `"canonical"`. Regression risk: if a future edit hardcodes the source string, every Vanguard PDF import drops to priority 4 and a stale manual price silently wins. Test lives in `tests/import/engine.test.ts::"derived prices inherit the parser sourceType"`.**

- **TWS snapshot price date is ET-anchored + trading-day-guarded (2026-05-31, `4702780`)**: `lib/tws/snapshot.ts::fetchSnapshotPrices` stamps prices with `todayET()` (NOT `new Date().toISOString()` — UTC) and **early-returns without writing when `isMarketClosed(today)`**. Root cause of the 5/29 "Significant Moves" bug: a late-ET sync stamped a frozen prior-session tick under the wrong day via UTC (`21:50 ET Sun → 6/01 UTC`), and weekend syncs wrote phantom non-trading-day rows. **Never** revert to a UTC date or drop the market-closed guard — every snapshot consumer (anomalies, valuations) treats the latest `prices` row per date as that date's close. Date is injectable via `options.asOfDate` (for tests). `DELAYED_FROZEN` is intentionally KEPT (the frozen close was accurate; the bug was the date) — see TODO "Official-bar daily-close capture" for the deferred byte-perfect-close increment.

- **Anomaly engine pins to a consecutive trading-day pair**: `lib/digest/anomalies.ts::computeAnomalies` (the "Significant Moves in Vanguard Holdings" engine, shared by the evening email + Today-tab `SignificantMovesCard`) resolves ONE `(latest, prior)` pair from SPY via `resolveTradingDayPair()` — filtering non-trading-day phantom rows with `market-holidays.ts` and requiring `nextTradingDay(prior) === latest` — then compares EVERY held name on those exact two dates. A security missing a close on either date is OMITTED (better under-report than a move computed across a gap/stale row). **Never** go back to each-security `MAX(date)` pairing (it let phantom weekend rows, stale funds, and the cross-day mislabel produce wrong moves). Guards tested in `tests/digest/anomalies.test.ts` (phantom-row-ignored / stale-skipped / non-consecutive→[]).

- **Anomaly trigger is a hybrid two-gate (2026-06-01, PR #22 `f96b0fe`)**: a Vanguard holding flags only when `|actualPct| >= 3.0` AND `z >= 2.0`, where `z = |actualPct − expectedPct| / residual_std` (`expectedPct = spyPct × beta`; `residual_std` = the stock's own idiosyncratic daily vol). Replaced the old `max(2×|expected|, 1.0%)` floor that **collapsed to the 1% floor on flat-index days** and flagged ordinary noise. Constants `MIN_ABS_MOVE_PCT=3.0` / `MIN_RESIDUAL_Z=2.0` / `RESIDUAL_STD_EPSILON=0.1` live in `lib/digest/anomalies.ts` and are **mirrored** in `workers/cron/src/fallback-evening.ts::evaluateAnomalies` (pure, exported; parity-tested — keep byte-identical incl. the `|| a.symbol.localeCompare(b.symbol)` sort tie-break). `residual_std` is persisted on `security_betas` (migration 056, PERCENT units) by `scripts/refresh-vanguard-betas.ts::computeBeta` and rides the R2 snapshot (`securityBetas[].residualStd`). **Graceful degradation**: when `residual_std` is null/≤epsilon the z-gate is skipped → 3% floor alone. `AnomalyFlag` carries `residualPct` + `zScore: number | null` (the removed `ratio`/`thresholdPct` are gone); the email + card render `Nσ` and show ALL flags (no cap).

- **Return-series code must guard against the `prices` multi-month gap (2026-06-01, `d174e89`)**: the `prices` table is NOT continuous — it mixes sparse month-end `canonical` statement anchors (last 2025-06-30) with dense daily `tws` rows (from 2026-03-27), leaving a ~9-month hole. Any `ln(price[i]/price[i-1])` over *adjacent rows* whose window reaches the anchor injects one giant "daily" return (real appreciation; a stock split for NFLX → β=−14.31). **Rule:** drop pairs where `lib/calendar/date-utils.ts::calendarDaysBetween(a,b) > 7`. Applied in `scripts/refresh-vanguard-betas.ts::computeBeta` (LIMIT-70 window reaches the anchor) and `lib/compute/risk.ts::computePositionRisk` (365-day window reaches it). NOT needed in `security-regression.ts` (252-day window stops before the anchor) or `daily_valuations`-based computes (that table starts 2026-03-27). See `memory/project_prices_gap_guard.md`.

- **Worker sibling fallbacks now bubble upstream failures (2026-05-31, `2313621`)**: the `fallback-digest.ts` error-counter pattern (`listErrors`/`articleErrors`/`lastError` → `kind:"error"` when all attempts fail) is mirrored across `fallback-briefing` / `fallback-evening` (wrap snapshot/Claude/Resend stages, return stage-named `kind:"error"`) and `fallback-earnings` / `calendar-enrich` (`lastError` on the result + `index.ts` `console.error` on total/partial failure). Any NEW Worker fallback path must track + bubble upstream errors the same way — a bare `catch { console.warn() }` is what hid the 6-day 5/20 outage.

- **Cloud-fallback travel hardening (2026-06-02, `4639df4` / Worker `08cbf6f5`)**: four fixes so the cloud carries more weight while the Mac is asleep. (1) **Evening email LIVE-fetches Gmail** — `runFallbackEvening` calls the shared `fetchAndProcessNewArticles(env, snap, {maxArticles:6})` extracted from `fallback-digest.ts`, so the day's afternoon newsletters (invisible in the frozen 2am snapshot, which is the bulk of an evening recap) appear instead of the evening silently skipping; bubbles `kind:"error"` when the fetch fails AND no other content (vs masking as `skipped:"no content"`). (2) **Anomaly-block Yahoo fetch batched** via the multi-symbol `spark` endpoint (`fetchLast2ClosesBatch`, 50 symbols/chunk): 71 Vanguard holdings went **72 → ~2 subrequests** — which ALSO repaired a latent bug (the per-symbol loop was over the 50-subrequest Workers free-tier cap, so the anomaly block silently never produced cloud output). Evening subrequest budget now ≤46 (`MAX_ARTICLES_PER_RUN_EVENING=6`, lower than the digest's 10 because the evening also spends Yahoo). (3) **Snapshot bumped to v5** (`scripts/snapshot-state-to-r2.ts` + Worker `state.ts`): adds `notes` (security-linked, 90d, content-capped) + `earningsBogeys` (curated consensus + whisper); `fallback-earnings.ts` renders both (`renderNotesBlock` / `renderBogeysBlock`, `resolveNotesForFamily` via issuer family, `resolveBogeysForEvent` by event_id), and the "limited cloud context" note is rewritten to disclose only what's STILL Mac-only (analyst recs, transcripts, sell-side web-search). Older Workers ignore the new fields (v5 back-compat). (4) **`enrich-fail` de-noise** (`calendar-enrich.ts::isBenignEnrichOutcome`): the Mac primary is unreachable from CF's edge on EVERY tick (Mesh CGNAT → CF 1016), so the `enrich-fail-{slot}` journal marker is cleared on a benign `no_candidates` outcome and kept only for real fallback failures (error / snapshot_missing / candidate-failures) — a quiet market day no longer reads as a wall of failures in the KV scan. **Verify-cloud gotcha:** `wrangler r2 object get --pipe` CACHES (served a stale byte-identical read for minutes) — to confirm a snapshot's real freshness/content, do a raw aws4fetch S3 GET (`Last-Modified` authoritative). See [[reference-r2-snapshot-debugging]]. Worker 181 tests; the evening live-fetch is proven equivalent to the digest's (same helper, which fetched 10 today-articles against a frozen snapshot).

- **IBKR headless OAuth data path (Tiers 2/3, 2026-06-03/04, `5568586`/`c36a95c`/`ec54aae`/`a354b9b`/`b1807f4`)** — first-party OAuth 1.0a (account is IBKR Pro), fully headless, no TWS/Gateway/browser. **Mac (Tier 2):** `lib/ibkr/{oauth-crypto,oauth-client,config,web-api,map-positions,refresh}.ts`; `refreshIbkrHoldingsFromWebApi(db,cfg)` reads positions/cost-basis/prices and **writes EXACTLY like the TWS sync** (holdings `source_key='tws-…'`, prices/snapshot `source='tws'`, then `computeDailyValuations`) so downstream needs zero changes; `/api/tws/auto-refresh` falls back to it when `getIbApi()` is null + OAuth configured. **Worker (Tier 3):** `workers/cron/src/ibkr-oauth.ts` is the WebCrypto+BigInt port (DH modexp + `subtle.sign` RSASSA-PKCS1-v1_5/SHA-256 + HMAC-SHA1/256; the RSA-PKCS1v1.5-decrypt "prepend" is a **constant** shipped as a secret — WebCrypto lacks that op). `workers/cron/src/ibkr-positions.ts` ports the mapper + adds the **snapshot↔live merge** + KV LST cache. Wired into `fallback-earnings` + `fallback-briefing` (both **best-effort → snapshot on any failure**, IBKR read **once per run** only when there's work). **Three invariants a future edit MUST keep:** (1) **live IBKR REPLACES the snapshot's IBKR-account rows for the family (matched by account-name `includes("ibkr")`), never APPENDS** — appending double-counts the same position; Vanguard/Roth snapshot rows stay (`combineFamilyPositions`). (2) The signature key ships to the Worker as **PKCS8 DER base64** (`openssl pkcs8 -topk8`), NOT the PKCS1 form `openssl genrsa` emits — WebCrypto `importKey` rejects PKCS1. - **Canonical CSV examples live in THREE places** that must stay in sync: `app/dashboard/components/CanonicalCsvGuide.tsx` (the Import-tab prompt generator — copy-paste target for Claude Co-Work preprocessing of Vanguard PDFs), `docs/canonical-csv-guide.md` (reference), and `tests/import/canonical-csv.test.ts` (fixtures). - **Canonical-CSV numeric parsing goes through `parseStrictNumber()`**: `lib/import/parsers/canonical-csv.ts` defines a single helper that returns NaN for any comma-bearing string. Use it for every numeric cell — never call `parseFloat()` directly on a CSV field. The native `parseFloat("1,234.56")` returns `1` (silent truncation, reads until first non-numeric char), which would silently corrupt comma-grouped amounts a Co-Work session might emit. With `parseStrictNumber` the existing `isNaN()` guards + `validate.ts` skip-with-warning behavior catches the bad row instead of committing wrong numbers. Hardened 2026-05-04 (`ff6059f`) pre-flighting an April-statement import.

- **Canonical-CSV transaction source_key includes integer cents**: `canonical:txn:{acct}:{sym}:{date}:{type}:{cents}` where cents = `Math.round(amount * 100)`. Pre-2026-05-04 the formula omitted cents and same-day same-symbol same-type fills (e.g., split sells of 400 + 100 RSP shares on the same day) collided silently via INSERT OR IGNORE. Always include amount-derived disambiguator on parser source_keys for any new file format that allows multiple fills per (account, security, date, direction). Migration 046 backfilled existing rows. Shipped 2026-05-04 evening (`33f3c63`). **The `:cents` disambiguator fails when amount is identical across rows — notably zero-amount gift/journal transfers** (two same-day `TRANSFER_OUT` of the same symbol both key `…:0`). As of 2026-06-05 (`e17477a`) the parser appends a stable `:#N` ordinal to the 2nd+ occurrence of any identical transaction source_key within a file (first keeps the bare key → already-imported rows stay idempotent on re-import; order-stable so re-import is a no-op). Co-Work prompt + `docs/canonical-csv-guide.md` carry the gifted/journaled-shares rule (`TRANSFER_IN`/`TRANSFER_OUT`, quantity = shares, amount = 0).

- **Canonical-CSV quantity is always positive — type carries direction**: parser auto-normalizes negative quantities to `Math.abs()` with a warning, so Co-Work output that follows the Vanguard-PDF signed-quantity convention (negative qty on sells) doesn't silently drop. Validator's `isValidQuantity` accepts any finite number. Pre-fix this rejected negatives and lost 16 VB + 4 Roth rows on April import. New code that adds parsers should mirror this convention: type field is the direction signal, not quantity sign.

- **Snapshot upsert priority — statement data wins over TWS placeholders**: `lib/import/engine.ts` snapshot insert uses `ON CONFLICT(account_id, month_end_date) DO UPDATE … WHERE source IN ('tws','manual')`. Statements (source ∈ {ibkr-activity, canonical, vanguard-pdf, …}) overwrite earlier TWS/manual rows; existing statement rows are preserved (idempotent re-imports). The matching `lib/tws/positions.ts` upsert is symmetric: TWS only writes when no statement row exists. Pre-2026-05-04 used INSERT OR IGNORE on engine side and INSERT OR REPLACE on TWS side, which meant whoever ran last won — IBKR April snapshot was a sparse `total_value`-only TWS row instead of the rich statement data with starting_value/twr/deposits.

- **Holdings upsert priority — statement data wins over TWS intra-day rows**: same pattern as snapshots, applied to holdings. `lib/import/engine.ts` holdings insert uses `ON CONFLICT(account_id, security_id, as_of_date) DO UPDATE … WHERE holdings.source_key LIKE 'tws-%'`. TWS auto-refresh writes intra-day positions to `holdings` with as_of_date=today and source_key=`tws-{accountId}-{securityId}-{today}`; if the day is also a statement period-end date, statement holdings (source_key prefix `ibkr:pos:`, `canonical:hold:`, etc.) must overwrite the TWS intra-day rows. Pre-2026-05-04 used INSERT OR IGNORE and 18 of 19 IBKR statement holdings were silently dropped on April-2026 import because TWS sync had run earlier in the day. Statement re-imports remain idempotent because the WHERE clause filters out non-tws source_keys.

- **Compare timestamps with SQLite `datetime()` on BOTH sides, never as raw strings**: `research_articles.received_at` and similar columns are written via `datetime('now')` in space-separator form ("2026-04-22 22:53:41"). Caller-supplied filters often arrive in ISO-Z form from `new Date().toISOString()` ("2026-04-22T13:44:44.806Z"). Under raw string compare, space (ASCII 32) < 'T' (ASCII 84), so space-format timestamps sort earlier than T-format ones even when the actual moment is later — silently returning zero rows. Always wrap both sides in `datetime()` when comparing timestamps that may mix formats. Shipped 2026-04-23 (`57d9c26`) after the "send digest since last email" bug.

- **Snapshot range boundaries BEFORE long awaits in concurrent endpoints**: `lib/digest/send-digest.ts::sendDigestEmail` reads `getLastDigestSentAt(db)` at function entry into a local `sinceSnapshot` variable, NOT inside the `since_last` branch which would run AFTER `syncPortfolio` + `fetchNewArticles` + `processUnprocessedArticles` (60-90s of awaits). Otherwise a concurrent manual trigger that completes during that window updates `last_digest_sent_at` to "now" and the cron path then reads a future-of-our-articles cutoff → zero matches → silent skip. This race produced 3 weekdays of mystery skips (Apr 22-24 2026). Pattern applies anywhere two paths can update the same "last X done" timestamp while one of them is mid-process. Regression test: `tests/digest/send-digest-race.test.ts`.

- **Calendar enrichment window is source-aware**: `lib/calendar/enrichment-runner.ts` keeps `MAX_AGE_MS_MACRO = 2h` (FRED/FOMC/nonfred publish data within minutes; immediate market reaction window is what matters) but uses `MAX_AGE_MS_EARNINGS = 12h` for `source = 'finnhub'` OR `event_type = 'earnings'`. - **Earnings date/slot verification — motivating incidents + live dry-run (migration 072, 2026-08-02)**: three live incidents in the 2026-07-30 earnings season exposed a gap the existing Conflicts tab (Finnhub-vs-Nasdaq disagreement) structurally cannot cover: (1) **RKT** previewed on a Nasdaq-only phantom 7/30 date — a single-source row never reaches the Conflicts tab because that surface only compares two vendors *against each other*, so a lone wrong vendor sails through unchallenged. (2) **LLY**'s active row for 8/05 carried the default 16:15 AMC slot while a *superseded* Nasdaq row (overwritten by a later Finnhub upsert) had the correct 08:00 BMO slot — the right answer existed in the data's history but not in the row the app reads. (3) **IMAX** (2026-07-23, already documented under the Earnings email sweep bullet) previewed after its real print because both vendors mis-slotted it. None of these are vendor-disagreement cases, so a same-day Claude+`web_search` pass against the *actual* wire/IR calendar is the only net that catches all three shapes. **Live validation**: a controller dry-run of `scripts/verify-earnings-dates.ts` on 2026-08-02 against the real DB found the tool works exactly as designed — 5 of 8 candidates were wrong vendor rows: MELI (8/03 → 8/05), RRX (8/04 → 8/05), LFMD (8/04 → 8/05), DOCN (slot AMC → BMO), and XMTR (slot AMC → BMO — this one would have shipped the XMTR preview email *after* the real print, an IMAX-class failure, had it gone unverified). **Design rule**: never edit a sync-owned row's `event_date`/`event_time` in place — the next Finnhub/Nasdaq upsert's `ON CONFLICT` clause re-clobbers it back to the wrong value on the very next sync tick, because sync sources are the row's owner and know nothing about the correction. Corrections instead go through `correctEarningsEventDate` (suppress the wrong sync-owned tuple via `calendar_event_suppressions`, migration 070 + `manual`-insert the corrected row) — same mechanism as `scripts/correct-earnings-date.ts`, extracted to a shared lib function so both the manual CLI and the new automated verifier call one code path. Corrected rows are excluded from re-verification once `date_verified_at` is stamped, and the sync upsert clears both `date_verified_at`/`date_verification_note` if a source subsequently moves `event_date` again (re-opens the row for the next verification pass rather than trusting a stale confirmation).
